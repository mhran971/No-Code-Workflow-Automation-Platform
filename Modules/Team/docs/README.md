# Team Module

Manages tenant staffing: employee user lifecycle (create/disable/enable/delete), teams, team membership, and manager promotion/demotion for the BusinessOwner → Manager → Employee hierarchy. Also owns a generic `audit_trails` log and two config-driven cross-table helpers (active-task reassignment, historical-data deletion guard) that other modules' data flows through without a hard model dependency.

## Services & Repositories

None of these extend `App\Services\BaseService` — every service takes its Repositories via plain constructor injection and manages its own atomicity with `DB::transaction()`/`DB::afterCommit()` closures *inside the service*, not in the controller. This differs from modules that follow the BaseService `__call()`-delegation convention. Repositories are also plain classes (no shared `BaseRepository` parent), registered as singletons in `TeamServiceProvider::register()` (lines 49-57).

| Class | File | Purpose |
|---|---|---|
| `TenantUserManagementService` | `app/Services/TenantUserManagementService.php` | Create/disable/enable/delete an Employee user, always scoped to `auth('api')->user()` being a `Role::BusinessOwner` acting on their own tenant. `createByBusinessOwner` (line 32) builds a random temp password (lines 39-48), creates the user, writes an audit row, calls `TeamMembershipRepository::ensureMember()` (lines 76-79), then queues `NewUserCredentialsMail` via `DB::afterCommit()` (lines 81-87) so the email only sends if the transaction commits. `disableByBusinessOwner` (line 98) delegates reassignment to `ActiveTaskReassignmentService` and aborts the whole transaction with an `HttpResponseException` (422, lines 122-127) if any table failed to reassign — the user is left enabled. `deleteByBusinessOwner` (line 193) first asks `HistoricalDataGuardService`; if any blocking records exist it returns `deleted: false` without touching the DB. |
| `TeamManagementService` | `app/Services/TeamManagementService.php` | List/show/create/update teams and replace a team's manager, all BusinessOwner- (or, for list/show, Manager-of-that-team-) gated. `createByBusinessOwner` (line 75) force-promotes the chosen manager to `Role::Manager` (line 94) and assigns their membership to the new team (lines 95-99). `updateManagerByBusinessOwner` (line 174) does the same for the new manager and auto-demotes the previous manager to `Role::Employee` **unless the previous manager is a BusinessOwner** (lines 200-206). `assertUserCanJoinTeam` (line 310) is the one-team-per-user guard used by both create and manager-replace paths. |
| `TeamMemberManagementService` | `app/Services/TeamMemberManagementService.php` | Add (single or bulk) / remove team members, gated to BusinessOwner or the team's own Manager (`assertCanManageTeamMembers`, line 163). `addMembers` (line 48) rejects any user already on a *different* team (lines 62-74) before writing anything. `removeMember` (line 112) refuses to remove the team's current `manager_id` (lines 120-124). |
| `ActiveTaskReassignmentService` | `app/Services/ActiveTaskReassignmentService.php` | Config-driven (`config('team.task_reassignment.tables')`) bulk reassignment: for each configured `{table, assignee_column, tenant_column, status_column, active_statuses}` spec it runs a plain `DB::table(...)->where(...)->update([...])`, guarded by `Schema::hasTable`/`hasColumn` so unknown tables/columns are silently skipped. Per-table `QueryException`s are captured into an `errors[]` array (not thrown) so the caller decides whether to abort. |
| `HistoricalDataGuardService` | `app/Services/HistoricalDataGuardService.php` | Config-driven (`config('team.deletion_guard.history_tables')`) read-only `COUNT` check across configured tables; returns a list of `{table, label, count, message}` blockers used to refuse permanent user deletion. **Unused scaffold route:** `routes/web.php` defines `Route::resource('teams', TeamController::class)` under session (`auth`,`verified`) middleware. `TeamController` (`app/Http/Controllers/TeamController.php`) is the stock `nwidart`-generated CRUD stub — `store`/`update`/`destroy` are empty method bodies, `index`/`show`/`create`/`edit` return placeholder Blade views (`resources/views/index.blade.php` literally renders "Hello World"). It is dead code, not part of the real product; the actual functionality is `TeamManagementController` + `TeamMemberController` + `MemberMangementController` above.

## Enums

None. The Team module defines no `app/Enums` directory of its own. It consumes `Modules\Auth\Enums\Role` (`BusinessOwner`, `Manager`, `Admin`, `Employee`) throughout for authorization. `TeamMembership.status` / `status_before_disable` and `ActiveTaskReassignmentService`/`HistoricalDataGuardService`'s config `active_statuses`/`history_statuses` are plain strings, not backed by a PHP enum.

There are also no `app/Exceptions` or `app/Policies` directories — authorization is done with inline checks throwing `Illuminate\Auth\Access\AuthorizationException` or `Illuminate\Validation\ValidationException` directly from services and `FormRequest::authorize()`, not via Laravel Policy classes.

## Key Business Rules & Gotchas

- **One team per user is app-enforced, not DB-enforced.** `TeamManagementService::assertUserCanJoinTeam` (line 310) and `TeamMemberManagementService::addMembers` (lines 62-74) both reject assigning a user who already has a *different* non-null `team_id` in their `TeamMembership`. The DB unique constraint on `team_memberships` is `[tenant_id, user_id]` (one row per user), which prevents duplicate rows but says nothing about team assignment itself.
- **Assigning a manager silently promotes/demotes roles.** Creating a team or calling `PATCH .../manager` force-sets the target user's `role` to `Manager` (`UserRepository::updateRole`). Replacing a manager auto-demotes the *previous* manager to `Role::Employee` — **unless** that previous manager is a `BusinessOwner` (`TeamManagementService.php` lines 200-206), in which case their role is left untouched. Since `resolveEligibleManager` (line 280) already refuses to let a BusinessOwner be selected as a new manager, this branch only guards legacy/edge data.
- **"Remove member" vs. "delete membership" are different operations.** `TeamMembershipRepository::removeFromTeam` only nulls `team_id` (row survives); `disable()`/`restore()` swap `status`↔`status_before_disable` (row survives); only `deleteForUser()` — called exclusively from `TenantUserManagementService::deleteByBusinessOwner` — actually deletes the row.
- **Disabling a user can fail loudly mid-transaction.** `disableByBusinessOwner` reassigns active tasks first; if `ActiveTaskReassignmentService` reports *any* per-table error, an `HttpResponseException` (422) is thrown **inside** the `DB::transaction()` closure, rolling everything back — the user is *not* disabled and no partial reassignment is kept.
- **`is_active` is enforced platform-wide, not just by Team endpoints.** The `is_active` column this module adds to `users` is checked by the global `EnsureActiveApiUser` middleware (`app/Http/Middleware/EnsureActiveApiUser.php:24-29`, aliased as `active.user` in `bootstrap/app.php:19`) on *every* authenticated API request across *all* modules, returning `403 "Your account is disabled..."`. Disabling a user through Team immediately locks them out of the entire platform, not just team features.
- **Cross-module side effects are config-driven table/column names, not FKs or Eloquent models.** `config/config.php`'s `task_reassignment.tables` (targets `tasks`, `workflow_tasks`, `instances`) and `deletion_guard.history_tables` (targets `instances`, `comments`, `notes`) are consumed via raw `DB::table()` queries guarded by `Schema::hasTable/hasColumn`. This means the two services silently no-op if a configured table/column doesn't exist (safe against drift) but will just as silently do nothing if someone typos an entry in the config (no validation/error surfaced).
- **Temp password + email side effect.** `TenantUserManagementService::createByBusinessOwner` (lines 39-48) builds a 12-character password with guaranteed upper/lower/digit/special characters via `str_shuffle`, then queues `NewUserCredentialsMail` (`app/Mail/NewUserCredentialsMail.php`) through `DB::afterCommit()` so it only sends once the user row is actually committed. A commented-out `Str::password(...)` alternative is left in place at line 38.
- **Self-service guard.** A BusinessOwner cannot disable/enable/delete their own account (`assertOwnerCanManageTarget`, `TenantUserManagementService.php` lines 239-252). When disabling someone without specifying `reassign_to_user_id`, tasks default to reassigning **to the BusinessOwner themselves** (`resolveTaskAssignee`, lines 261-263).
- **`manager-candidates` filtering.** `MemberMangementController::managerCandidates` (lines 40-55) excludes BusinessOwners, inactive users, and anyone whose membership already has a non-null `team_id` — but does so with a raw `leftJoin` on `team_memberships` + `whereNull('tm.team_id')` (see `baseTenantUsersQuery`, lines 160-180), not through the `Team`/`TeamMembership` Eloquent relations.

## Cross-Module Dependencies

- **Auth (`Modules\Auth`) — bidirectional, tightly coupled.** `Team`/`TeamMembership` both `belongsTo` `Modules\Auth\Models\User`, and `Team` also `belongsTo` `Modules\Auth\Models\Tenant`. Conversely, Auth's `User` model (`Modules/Auth/app/Models/User.php`) imports `Modules\Team\Models\Team` and defines `getManagedTeam()` (lines 96-103): `hasOne(Team::class, 'manager_id')->where('tenant_id', ...)`. Auth's `SessionController::me()` (`Modules/Auth/app/Http/Controllers/SessionController.php:58-86`) also queries `TeamMembership::with('team')` directly (lines 64-66) to surface `team: {id, name}` in the `GET /api/v1/me` payload — Team exposes no "my team" endpoint of its own; Auth reaches into Team's model directly.
- **Tenancy is fully manual.** Both `Team` and `TeamMembership` carry their own `tenant_id` column (not derived through a relation/global scope), and every service method re-checks `(int) $actor->tenant_id === (int) $target->tenant_id` by hand. There is no shared tenant-scoping trait or Eloquent global scope anywhere in this module.
- **Workflows (`Modules\Workflows`) is the heaviest consumer** — every workflow belongs to exactly one team, and team membership drives authorization, task assignment validation, and inbox scoping:
  - `Workflow` model has a `team_id` FK and `belongsTo(Team::class)` (`Modules/Workflows/app/Models/Workflow.php:14,28,62-65`).
  - `WorkflowAuthorizationService::canView/canManage` (`Modules/Workflows/app/Services/WorkflowAuthorizationService.php`) gates access by team: BusinessOwner sees everything; Manager only if `Team.manager_id === actor.id` for that workflow's team (lines 69-74); Employee only if an *active* `TeamMembership` ties them to the workflow's team (lines 36-42).
  - `WorkflowManagementService::createWorkflow` (`Modules/Workflows/app/Services/WorkflowManagementService.php:82`) requires a Manager's `getManagedTeam()` to be non-null and requires an explicit `team_id`, validated against `Team::where('tenant_id', ...)` (lines 88-101).
  - **Verification pipeline stage 4** (`ContextualVerificationRule`, `Modules/Workflows/app/Services/Verification/Rules/ContextualVerificationRule.php:66-75`) checks that any `task-node`'s `config.assignTo` is both an active tenant user *and* an active `TeamMembership` member of the workflow's team, else it raises `context.assignee_not_team_member`.
  - `WorkflowTaskController::teamMemberIds()` (`Modules/Workflows/app/Http/Controllers/WorkflowTaskController.php:152-162`) scopes a Manager's human-task inbox to `assignee_id IN (their team's member user_ids)` via `Team::where('manager_id', ...)->with('memberships')`.
  - `DynamicFlowController` (`Modules/Workflows/app/Http/Controllers/DynamicFlowController.php`) both queries `Team` directly to authorize dynamic-flow design ("creator or team manager", lines 171-178) **and** injects Team's own `AuditTrailRepository` (constructor line 26, used at line 134) to write audit rows into Team's `audit_trails` table directly — Workflows writes into Team's repository rather than Team publishing an event/service API for it.
  - **Known inconsistency to flag if touching either side:** `Workflow::scopeVisibleTo()` (`Modules/Workflows/app/Models/Workflow.php:91-121`, Manager branch at lines 102-105) reads `$actor->managedTeam->id` — a `managedTeam` *property*, which does not exist as a relation or accessor anywhere on `User` (only the differently-named method `getManagedTeam()` exists). This will resolve to `null` via Eloquent's magic getter and throw on `->id` for any Manager whose code path hits this scope. Not part of Team's own code, but rooted in Team's manager-relationship contract.
- **One-directional, string-only coupling:** Team's `config/config.php` references Workflows' `workflow_tasks`/`instances` tables by name (for `task_reassignment` / `deletion_guard`) without any PHP class dependency — Team has no `use Modules\Workflows\...` anywhere in its own code.
- **Integrations module:** no real dependency. A `'teams'` array key in `Modules/Integrations/app/Services/Drivers/ClickUpDriver.php` refers to ClickUp's own external "team" API concept and is unrelated to this module.
